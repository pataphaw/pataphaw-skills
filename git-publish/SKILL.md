# Git Publish

## 目标与执行范围

先理解每项改动的目的和依赖，再组织成便于审阅、验证和回退的一组提交，完成推送和 PR。分析改动是决定 commit 粒度的内部步骤。

用户要求完整发布或直接调用本 skill 发布当前改动时，默认完成提交、推送 `origin`、向 `main` 创建或更新 PR。用户明确限定“只拆分提交”“不推送”“只推送、不建 PR”等范围时，执行到指定阶段；只要求拆分建议或提交信息时，仅提供文本。范围已明确时直接推进，不把拆分方案作为额外审批步骤。

## 工作流
### 1. 理解范围、意图与依赖

- 运行 `git status -sb`，检查当前分支、暂存区、未暂存及未跟踪文件，以及是否有未完成的 merge、rebase 或 cherry-pick。
- 结合 `git diff`、`git diff --cached` 和必要的上下文阅读，理解每项改动解决的问题；未跟踪文件需单独阅读，不能只凭文件名归类。
- 范围由用户请求及已有对话确定。已明确属于其他任务的改动留在原处；用户要求发布全部改动时，可按多个意图拆分，不必因主题不同再次询问。只有归属不清且会影响提交内容时才询问。
- 已暂存内容也要纳入范围检查。需要调整暂存边界时仅处理本次范围内的路径或补丁；不要清空整个暂存区或覆盖工作区改动。

### 2. 判断要不要切分支

- 检查 remote、upstream 和已有提交；在判断与远端的差异或发布前，fetch 相关远端引用。无法获取最新状态时说明限制，不把缓存当作实时状态。
- 如果当前在 `main`、`master` 或其他默认分支上，先创建独立工作分支。分支名使用 `codex/<topic>`，简短表达这次工作的主题，除非用户另有指定。
- 当前特性分支适合本次工作且尚在使用时继续使用；已有 PR 时检查其状态及目标分支。
- 若原 PR 已合并或关闭，或分支内容已通过 squash 等方式进入目标分支，通常从最新目标分支创建新的工作分支，并妥善承接本次改动。结合 PR 状态、补丁等价性和文件差异判断，不只比较提交 SHA。
- 切换前确保本地改动可保留。需要处置未完成的 Git 操作、覆盖改动或改写已有历史时，先说明具体问题并确认处理方式。

### 3. 按意图拆分提交

- 以“这一笔完成了什么”为单位分组，不按文件数、目录或 diff 行数机械切分。一个跨多文件的完整功能可以是一笔；同一个文件里的两个独立修复可以分成两笔。
- 能独立解释、验证和回退的不同目的优先分开；实现同一行为所必需的代码、配置、测试、文档和调用处应放在一起。避免把实现和必需的适配拆开，留下明显不可用的中间提交。
- 按依赖排序：独立且保持行为不变的准备性重构可以先提交，再提交依赖它的功能或修复。不为凑提交数量拆出没有独立价值的小步。
- rename / move 或批量格式化只有在可独立成立、且能明显简化 review 时才单独提交；重命名所需的引用更新应同时完成。若拆开会破坏中间状态或掩盖一个完整意图，则合并提交。
- 执行前简要列出每笔提交的目的、范围和顺序，然后继续操作。已有用户提交只做检查，不擅自拆分、amend、squash 或重排。
- 显式按路径暂存；同一文件混有多个意图时按 hunk 或精确补丁暂存。不要为了方便把无关内容一起加入。
- 每笔提交前检查完整 `git diff --cached`，确认实际暂存内容与该笔意图一致、没有遗漏依赖，也没有混入其他已暂存改动。

### 4. 写精心的 commit message

- 遵循仓库现有约定；没有约定时，用简洁的祈使语气描述这笔提交带来的具体变化。
- 标题对应一个意图。若必须用多个不相关的主题才能概括，重新检查拆分是否合理。
- 必要时在正文补充动机、取舍或兼容性影响，不重复罗列文件名，不把未做的验证写成已完成。

### 5. 做轻量但有价值的验证

- 每笔提交前运行 `git diff --cached --check`，并完成仓库要求及与改动相关的检查。
- 确保验证对象与声称的范围一致：在包含后续未提交改动的工作区跑过测试，不能据此声称每个中间提交独立通过。拆分存在依赖疑点时，在隔离目录或 worktree 验证对应提交。
- 推送前检查最终 diff、提交顺序和剩余工作区状态，确保没有遗漏本次范围内的内容。保留相关验证结果和无法验证的限制。

### 6. 默认推送远端

- 在本次执行范围包含推送时，默认推送到 `origin`；用户指定其他 remote 时遵循其选择。必要时使用 `git push -u <remote> <branch>` 建立跟踪关系。
- 没有新文件改动时，仍检查已有未推送提交或待创建的 PR；若内容已经发布，报告现状，不制造空提交。
- 推送失败时定位原因；遇到远端分叉，不自动强推或改写历史。若因权限或网络无法继续，明确说明阻塞点。

### 7. 默认创建 PR

- 在本次执行范围包含 PR 时，推送后创建或更新 PR。用户未指定目标分支时使用 `main`；仓库没有 `main` 时检查远端默认分支。
- 同一分支和目标已有开放 PR 时复用，并让标题、正文反映最终改动；不要重复创建。没有实际差异时不创建空 PR。
- 默认创建普通 PR；用户明确表达 WIP / draft，或改动明显尚未准备好 review 时使用 draft。未经要求不合并 PR。
- 优先使用可用的 GitHub connector，必要时使用 `gh`。多行正文用结构化参数或临时文件配合 `--body-file` 传入，保留换行并避免 shell 展开。
- 标题概括最终变更，正文先说明解决的问题和结果，再按复杂度补充影响、取舍和验证。不要把操作过程或对话历史当作 PR 描述。

## 输出要求

汇报最终分支、每笔新提交的 SHA 与标题、推送状态、PR 链接与目标分支，以及验证结果。若有意留出了其他改动或某一步受阻，简要说明；未执行的步骤不要声称完成。
